# Edit File: A Robust 9-Pass Fuzzy Matching Algorithm for LLM-Driven Code Edits

To elevate the patch success rate of lightweight locally hosted models to match that of larger models, the core execution logic of the edit_file tool must feature an advanced, multi-layered fuzzy matching algorithm. A strict exact-match edit tool causes the majority of agent errors in practice, not because the agent's intent is wrong, but because its reproduction of the target text is slightly off.

Rather than blindly failing when old_text does not exactly match a substring in the target file, the tool must iteratively apply a sequence of progressively relaxed matchers. This architecture implements a "Chain of Responsibility" pattern. The chain short-circuits on the first successful match, meaning that if the LLM provides an exact match, the operation incurs zero computational overhead from the subsequent fuzzy passes. Crucially, each replacer class in the chain returns the actual substring found in the original file, rather than the LLM's hallucinated query, ensuring that the final replacement preserves the file's original formatting.

The following details the optimal 9-pass fuzzy matching chain required to absorb the variance of SLM outputs.

## Pass 1: The Exact Literal Match

The initial pass performs a standard literal string search. If old_text exactly matches a sequence in the file, the replacement is executed. However, to prevent catastrophic patching, this pass enforces strict uniqueness verification. The system verifies that the old_text block appears exactly once in the file. If multiple exact matches exist, the tool rejects the edit and returns an error requesting the LLM to provide a larger context block to anchor the change uniquely. Additionally, a stale-read validation check is performed to reject edits to files that have been modified since the agent's last read_file operation, preventing race conditions in multi-agent environments.

## Pass 2: Whitespace Invariance and Normalization

If the exact match fails, the second pass addresses the most common SLM hallucination: whitespace variance. SLMs frequently output incorrect spacing, convert tabs to spaces, or drop trailing newlines due to how code is stripped during training data preparation. The algorithm collapses all contiguous whitespace characters (spaces, tabs, newlines) in both the target file and the old_text payload into single spaces. If a unique match is found in this normalized lexical space, the algorithm mathematically maps the boundary indices back to the original, un-normalized file string, executing the replacement without altering the surrounding whitespace.

## Pass 3: Relative Indentation Preservation

Incorrect indentation accounts for a vast majority of failed S/R blocks, particularly in Python. SLMs often generate code that is correctly structured internally but "flushed left" or misaligned relative to the target file's nested scope. In Pass 3, the algorithm calculates the relative indentation of the old_text block. Drawing inspiration from tools like RooCode and advanced Neovim plugins, the system captures the original leading whitespace of the matched lines in the file. It then analyzes the calculated indentation of each line within the new_text replacement block relative to its first line. By re-applying the captured original indentation style while maintaining the calculated relative structure of the replacement code, the tool neutralizes indentation drift entirely.

## Pass 4: Escape Sequence and String Literal Unpacking

Models often fail to correctly escape nested quotes, regex patterns, or complex string literals, particularly when dealing with cross-language generation (e.g., generating JSON containing escaped Bash scripts). Pass 4 processes both the source file and the old_text through string literal unescaping mechanisms. It attempts to find a match where the raw string values align, even if the syntactical escaping generated by the model deviates from the codebase's standard implementation.

## Pass 5: Algorithmic Edit Distance (Damerau-Levenshtein)

When structural normalizations fail, the tool descends into advanced algorithmic fuzzy string matching. The algorithm calculates the minimum number of edits required to transform the hallucinated old_text into a block in the source file using Levenshtein distance principles. Crucially, the system should employ the Damerau-Levenshtein variant, which accounts for character transpositions—a highly common cause of typos and tokenization misalignments in LLMs. If a contiguous block in the file yields an edit distance similarity score above a strict threshold (e.g., 90%), it is flagged as a match.

## Pass 6: Lexical Token Sorting and Set Ratios

Sometimes a model will recall the correct logical components of a function but output them in a slightly altered sequence (e.g., swapping parameter orders in a function signature hallucination). Pass 6 utilizes tokenization and alphabetization before matching. Using logic mirrored in libraries like TheFuzz, the text is split into tokens, sorted alphabetically, and then matched using intersection and remainder comparisons (Token Sort Ratio and Token Set Ratio). This step overcomes SLM hallucinations where the intent is pristine but the syntactic ordering is mildly scrambled.

## Pass 7: Semantic Duplicate Detection and Vector Embeddings

If purely lexical fuzzy matching fails, the system shifts to semantic duplicate detection. This pass transforms the old_text into a dense vector representation using a lightweight embedding model (e.g., SBERT) and compares it against chunked embeddings of the target file. This approach ensures that even if the SLM used drastically different variable names or formatting in its old_text block, the underlying semantic intent can anchor the patch to the correct region. Utilizing dimensionality reduction techniques like Non-negative Matrix Factorization (NMF) within libraries like Neofuzz ensures this semantic matching executes rapidly via cosine similarity metrics.

## Pass 8: Abstract Syntax Tree (AST) Structural Matching

For heavily structured languages (Python, Rust, C++), Pass 8 parses the file into an Abstract Syntax Tree (AST) and queries the tree for the semantic node implicitly targeted by the LLM. Rather than relying on text strings, the edit_file tool uses structural identifiers (e.g., ast-grep) to locate the exact basic block corresponding to the target logic, entirely ignoring comments, docstrings, and syntactic sugar. This technique relies on proving semantic equivalence between the model's generated block and the original block, rendering the match resilient against single insertions, the splitting up of computations, and generalized code bloat.

## Pass 9: Context-Aware Anchor Bounding Boxes

The final pass attempts to match based solely on the first and last lines of the old_text block, treating them as semantic anchors. SLMs, prone to the lazy coding phenomenon, often generate correct headers and footers for a code block but summarize or hallucinate the middle of the block with comments like ... rest of code.... By identifying unique anchors at the start and end of the block, the algorithm extracts the exact intermediary lines from the original file, dynamically reconstructing the correct replacement target and successfully bridging the gap over the model's truncated output.
